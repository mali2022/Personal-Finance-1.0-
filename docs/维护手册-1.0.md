## 1. 系统组成与运行环境

> **适用场景**：第一次在本机部署、换机迁移、或需要判断某个组件是否属于本系统时，先读本节。

### 1.1 组件清单

| 组件 | 位置 | 技术栈 | 职责 |
| --- | --- | --- | --- |
| 前端单页应用 | frontend/ | React 19 + TypeScript + Vite | 记账界面、报表、设置、版本公告 |
| 后端 API 与静态托管 | backend/src/PersonalFinance.Api/ | ASP.NET Core 10 + EF Core | 业务规则、鉴权、静态资源、健康检查 |
| 领域 / 契约 / 基础设施 | backend/src/PersonalFinance.Domain/、PersonalFinance.Contracts/、PersonalFinance.Infrastructure/ | C# | 实体、请求模型、映射与持久化 |
| 本地数据库 | SQL Server 默认实例（服务名 MSSQLSERVER） | SQL Server | 库名 PersonalFinanceWeb |
| 本地启动器 | scripts/PersonalFinance.Local.ps1 | PowerShell | 环境校验、起停进程、就绪探测 |
| 备份与审计脚本 | backend/scripts/ | PowerShell 7 | 备份、校验、隔离恢复、只读审计 |
| 双击入口 | 仓库根目录各 *.bat | cmd | 转调启动器与自启动脚本 |

### 1.2 端口与地址

| 端口 | 使用者 | 地址 | 说明 |
| --- | --- | --- | --- |
| 5085 | 后端 API | http://127.0.0.1:5085/ | -Static 模式下同时是站点首页；2026-11-18 及以前为 5080 |
| 5085 | 健康检查 | http://127.0.0.1:5085/api/health | 返回 status 与 buildId |
| 5174 | Vite 集成模式前端 | http://127.0.0.1:5174/ | 不加 -Static 时的访问地址，/api 反向代理到 5085 |

端口 5085 自 1.0.0 正式版（发布号 2026.11.18.1）起使用，2026-11-18 及以前为 5080。桌面版「个人记账」（%LOCALAPPDATA%\Programs\PersonalFinance，快捷方式参数 --desktop）默认占用 5080，两者同时打开时后启动的一方会报「后端端口 5080 已被占用」，因此本副本改用 5085。
| 5173 | 演示界面 | http://127.0.0.1:5173/ | 由"打开演示界面.bat"启动，不连接数据库 |
| 4173 | 前端 preview | http://127.0.0.1:4173/ | 仅本地预览构建产物，日常维护不使用 |

### 1.3 三种运行形态

- **Debug 运行版本**：由 dotnet build 产出的 backend/src/PersonalFinance.Api/bin/Debug/net10.0/PersonalFinance.Api.dll，启动器直接用它托管服务。这是本机日常使用的默认形态。
- **静态 wwwroot 模式（-Static）**：后端把 backend/src/PersonalFinance.Api/wwwroot 作为站点根目录，单进程、单端口，前端构建产物必须事先复制到该目录。
- **Vite 开发模式（不加 -Static）**：前端 dev server 与后端 API 两个进程并存，前端读取 frontend/node_modules/vite/bin/vite.js，改代码即时生效，适合开发与联调。

### 1.4 版本与依赖要求

| 依赖 | 最低要求 | 校验点 |
| --- | --- | --- |
| Node.js | 20 | 非 -Static 模式启动时校验主版本，低于 20 直接报错退出 |
| .NET SDK / 运行时 | 10 | 启动器解析 dotnet 后校验主版本，低于 10 直接报错退出 |
| PowerShell | 7 | 备份类脚本头部 #Requires -Version 7.0 |
| SQL Server | 默认实例 MSSQLSERVER | 启动前检查服务存在与可连接 |
| sqlcmd | 随 SQL Server 客户端提供 | "备份并升级本地数据库.bat"依赖它执行备份与校验 |

启动器的运行时解析顺序为：local-runtime.json 配置值 → 环境变量 → PATH → 内置候选目录。因此换机后即使不装到默认位置，也可以通过配置或环境变量指向可执行文件，无需改动脚本。

### 1.5 目录约定

| 路径 | 用途 | 是否可删除 |
| --- | --- | --- |

| deploy/ | 部署资料 | 否，内部信息不在本文展开 |

## 2. 启动、停止与状态查看

> **适用场景**：每天开机后启动系统、临时停掉服务、或怀疑进程状态与实际不符时使用本节。

### 2.1 双击链路

| 双击文件 | 实际动作 |
| --- | --- |
| 启动PersonalFinance.bat | 转调 打开PersonalFinance.bat，并透传命令行参数 |
| 快速进入.bat | 与 启动PersonalFinance.bat 等价 |
| 打开PersonalFinance.bat | 以 UTF-8 代码页调用 powershell.exe，执行 scripts/PersonalFinance.Local.ps1 -Mode Start -Static -ConfigPath scripts/local-runtime.json |
| 停止PersonalFinance.bat | 执行 scripts/PersonalFinance.Local.ps1 -Mode Stop |
| 设置登录自启动.bat / 关闭登录自启动.bat / 删除登录自启动.bat | 执行 scripts/PersonalFinance.Autostart.ps1 -Mode Enable / Disable / Delete |
| 打开演示界面.bat | 启动 Vite 演示站点（5173），不连接数据库、不写正式账本 |
| 备份并升级本地数据库.bat | 手工确认后备份数据库并执行结构升级，见第 5、6 章 |

打开PersonalFinance.bat 的核心命令行是：

```bat
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File "%~dp0scripts\PersonalFinance.Local.ps1" -Mode Start -Static -ConfigPath "%~dp0scripts\local-runtime.json" %*
```

启动失败时窗口不会自动关闭，会提示到 .local-run\logs 查看日志。

### 2.2 直接调用启动器

启动器参数与默认值如下（与脚本 param 块一致）：

| 参数 | 取值 | 默认 | 作用 |
| --- | --- | --- | --- |
| -Mode | Start / Stop / Status | Start | 启动、停止、查看状态 |
| -Static | 开关 | 关闭 | 用 wwwroot 静态站点托管，不启动 Vite |
| -NoBrowser | 开关 | 关闭 | 就绪后不自动打开浏览器 |
| -ConfigPath | 文件路径 | scripts/local-runtime.json | 运行时配置（可执行文件路径与端口） |
| -StateDirectory | 目录路径 | 仓库根 .local-run | 日志、进程记录、锁文件所在目录 |
| -ReadyTimeoutSeconds | 整数 | 60 | 就绪探测超时秒数 |

常用命令：

```powershell
# 静态模式启动，不弹浏览器（最常用于排查）
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Start -Static -NoBrowser

# 开发模式启动（Vite 5174 + 后端 5085）
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Start -NoBrowser

# 停止（只停启动器创建的进程）
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Stop

# 查看状态
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Status

# 首次启动慢、机器性能不足时放宽就绪超时
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Start -Static -NoBrowser -ReadyTimeoutSeconds 120
```

### 2.3 启动器的检查顺序

启动器按固定顺序执行校验，任一环节不通过即退出，不会"带病启动"：

1. 加独占锁 launcher.lock，防止两个实例同时操作；第二个实例报"另一次启动或停止正在执行，请稍后再试。"。
2. 读取运行时配置，解析 node 与 dotnet 可执行文件。
3. 版本校验：非 -Static 时要求 Node 20 及以上；任何模式都要求 dotnet 主版本 10 及以上。
4. 读取后端配置中的数据库连接项，确认指向本机默认实例且库名为 PersonalFinanceWeb，否则拒绝启动，并声明不修改配置或数据库。
5. 检查 MSSQLSERVER 服务是否存在、是否运行；未运行则尝试启动，权限不足时改走管理员辅助脚本。
6. 用一次最小查询确认数据库可连接。
7. 检查已构建的后端 DLL 是否存在。
8. -Static 模式下检查 wwwroot/index.html；普通模式下检查前端 vite 入口文件。
9. 比较源码时间戳与 DLL 时间戳，源码更新则要求先重新构建。
10. 检查端口占用，判断占用者是否是本项目健康实例。
11. 拉起进程、轮询就绪地址，就绪后输出访问地址并按需打开浏览器。

### 2.4 成功标志与访问地址

- -Static 模式就绪后输出"已就绪：http://127.0.0.1:5085/"。
- 普通模式就绪后输出"已就绪：http://127.0.0.1:5174/"。
- 未指定 -NoBrowser 时会自动打开默认浏览器。
- 就绪判定要求 HTTP 200；API 还要求响应 JSON 中的 status 等于 healthy；页面还要求内容包含站点标题。

手工确认可用：

```powershell
Invoke-RestMethod http://127.0.0.1:5085/api/health
```

正常返回包含 status、code、buildId 三个字段，其中 code 为 READY 表示程序与数据库结构一致。

### 2.5 日志与进程记录

| 文件 | 位置 | 用途 |
| --- | --- | --- |
| 启动/停止日志 | .local-run\logs\<yyyyMMdd-HHmmss-fff>-<Mode>.log | 记录本次操作每一步的结论与报错 |
| 进程记录 | .local-run\processes.json | 记录启动器创建进程的 PID、创建时间、可执行文件与命令行 |
| 互斥锁 | .local-run\launcher.lock | 保证同一时刻只有一个启动或停止操作 |

排查任何启动问题的第一步都是打开"最新的一份日志"，而不是反复重启。

### 2.6 停止语义

"停止"只结束启动器自己创建的进程，判断依据是 PID、进程创建时间、可执行文件路径与命令行四者同时匹配进程记录；满足条件才会结束，并且连同其子进程一起结束。完成后输出提示，明确未由启动器创建的服务、SQL Server 与浏览器都保留运行。

因此以下行为都是错误的，会造成误杀其他程序：

- 用任务管理器批量结束后端 dotnet 进程。
- 用命令一次性杀掉所有 node 进程。
- 在数据库仍在被其他程序使用时强行重启 SQL Server 服务。

### 2.7 状态查看

-Mode Status 会读取进程记录并逐项核对，输出"运行中"或"已退出或身份不匹配"，同时打印日志目录。判断"服务到底在不在"应当以它为准，而不是以窗口是否还开着为准：启动器窗口关闭不代表服务停止，服务也可能在窗口关闭后崩溃。

### 2.8 登录自启动

自启动通过 Windows 计划任务实现，由 scripts/PersonalFinance.Autostart.ps1 管理：

| 属性 | 取值 |
| --- | --- |
| 任务名 | PersonalFinance- 前缀加仓库根路径哈希的前 12 位 |
| 触发 | 用户登录时，延迟 30 秒 |
| 运行级别 | 交互式、普通权限（不提权） |
| 多实例 | 忽略新实例，避免重复启动 |
| 单次执行上限 | 5 分钟 |
| 查询 | scripts/PersonalFinance.Autostart.ps1 -Mode Status |

删除自启动用 -Mode Delete；该操作只影响计划任务，不删除程序与数据。

## 3. 静态模式与开发模式

> **适用场景**：需要选择用哪种方式打开系统、或遇到"前后端版本不一致""页面打不开"时使用本节。

### 3.1 两种模式对照

| 维度 | 静态模式（-Static） | 开发模式（不加 -Static） |
| --- | --- | --- |
| 进程数 | 1（仅后端） | 2（后端 + Vite） |
| 访问地址 | http://127.0.0.1:5085/ | http://127.0.0.1:5174/ |
| 前端来源 | backend/src/PersonalFinance.Api/wwwroot | frontend/ 源码，实时编译 |
| 必需产物 | wwwroot/index.html | frontend/node_modules/vite/bin/vite.js |
| Node 校验 | 不需要 | 需要 Node 20 及以上 |
| 改前端代码 | 必须重新构建并回写 wwwroot | 保存即生效 |
| 是否适合日常使用 | 是，双击入口即此模式 | 适合开发与联调 |

### 3.2 静态模式的前置条件与准备

1. 前端已完成生产构建，产物在 frontend/dist。
2. 产物已复制到 backend/src/PersonalFinance.Api/wwwroot，且存在 index.html。
3. 后端已构建，bin/Debug/net10.0/PersonalFinance.Api.dll 存在且不早于源码。
4. 数据库结构不低于程序版本要求。

复制产物的命令（仓库根执行）：

```powershell
Copy-Item -Path .\frontend\dist\* -Destination .\backend\src\PersonalFinance.Api\wwwroot -Recurse -Force
```

缺少 index.html 时启动器不会猜测，而是提示先把 frontend/dist 复制到 wwwroot，或改用普通模式启动。

### 3.3 开发模式的前置条件

1. frontend/node_modules/vite/bin/vite.js 存在；缺失先执行前端依赖安装。
2. Node 版本不低于 20。
3. 后端已构建。

开发模式下前端 dev server 监听 5174，并把 /api 请求代理到 5085；代理目标可由环境变量覆盖，默认为本机回环地址的后端端口。

### 3.4 关键报错与处理

| 报错关键句 | 触发条件 | 处理 |
| --- | --- | --- |
| 后端源代码已更新，但 Debug 运行版本尚未重新构建 | 后端 .cs/.csproj 修改时间晚于 DLL | 先停止本地服务，再执行 dotnet build backend/src/PersonalFinance.Api --no-restore，然后重新启动 |
| 缺少已构建后端 | DLL 不存在 | 先按文档构建后端，启动器不会自动构建或迁移数据库 |
| Node 版本过低 | 主版本低于 20 | 安装 Node 20 及以上，或在配置中指向新版本 |
| dotnet 版本过低 | 主版本低于 10 | 安装 .NET 10 SDK 或运行时 |
| 缺少前端依赖 / 提示安装依赖 | 无 vite 入口文件 | 安装前端依赖，或改用 -Static |
| 静态站点文件缺失 | wwwroot/index.html 不存在 | 复制 frontend/dist 到 wwwroot，或改用普通模式 |
| 启动超时 | 超过 -ReadyTimeoutSeconds | 查看本次日志定位卡在哪一步，必要时放宽超时 |
| 数据库结构落后（SCHEMA_OUTDATED） | 程序已升级但库未升级 | 先备份数据库，再执行"备份并升级本地数据库.bat"，或按第 6 章执行结构升级 |

完整命令：

```powershell
dotnet build backend/src/PersonalFinance.Api --no-restore
```

"源码更新但未重建"是最常见的启动失败原因：改了后端代码后忘了构建，启动器宁可拒绝启动，也不愿让新旧版本混跑。

### 3.5 常见误解

- 认为双击就是开发模式：双击入口固定带 -Static，属于静态模式。
- 认为构建前端后立即生效：静态模式下必须把 dist 回写到 wwwroot 并重启后端。
- 认为启动器会自动构建或自动升级数据库：两个"不会"都是设计如此，日志与报错原文都写明了。

## 4. 常见故障排查

> **适用场景**：启动失败、页面打不开、登录异常、保存报错、报表数字可疑时，按本节顺序排查。

### 4.1 排查顺序

1. 看最新日志：.local-run\logs 下按时间排序取最后一份。
2. 看状态：-Mode Status，确认进程是否真的在运行。
3. 看端口：确认 5085 / 5174 的占用者是不是本项目实例。
4. 看健康检查：/api/health 的 status 与 code。
5. 看数据库：实例服务是否运行、库名是否为 PersonalFinanceWeb、结构是否落后。
6. 看版本：前后端产物是否一致，前端是否已回写 wwwroot。

### 4.2 故障速查表

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 双击后窗口一闪而过 | 参数透传或脚本报错 | 改用命令行直接调用启动器，看完整报错与日志 |
| 端口被占用，且不是本项目健康的后端 | 其他程序占用 5085 / 5174 | 核对占用程序后自行决定是否关闭，启动器不会强行结束它 |
| 与桌面版「个人记账」同时打开后提示后端端口被占用 | 桌面版默认占用 5080，旧副本（2026-11-18 及以前）也用 5080 | 本副本自 1.0.0 正式版（2026.11.18.1）起用 5085；确认双击的是本副本的启动器，或只保留一方运行 |
| 提示"已经健康运行，直接复用" | 上一实例仍在运行 | 属正常复用，需要重启时先执行 -Mode Stop |
| 启动后页面 404 | 静态模式缺 index.html，或访问了错误的端口 | 回写 wwwroot 产物后重启；确认访问 5085 还是 5174 |
| 访问 /api 下未知路径返回 404 | 未知接口按约定返回 404，不返回首页 | 属预期行为，核对接口路径 |
| 登录后刷新即失效 | 会话或签名密钥配置异常 | 检查后端受保护配置是否完整，必要时重新登录 |
| 保存时提示数据已更新，请刷新后重试 | 并发修改导致的版本冲突 | 刷新后重试，不要强行覆盖 |
| 保存时提示请求重复或幂等冲突 | 幂等键相同但请求内容不同 | 改用新的请求标识，或确认是否为重复提交 |
| 提示数据库结构落后 | 程序已升级，库未升级 | 先备份，再升级结构 |
| 提示数据库无法连接 | 实例未运行、库不存在、配置指向错误 | 启动服务、核对库名与配置，不修改真实库 |
| 备份失败 | 磁盘空间不足、权限不足、服务不可用 | 清理空间或提升权限后重试；失败记录留在备份目录的 manifest 与错误日志中 |
| 恢复校验指纹不一致 | 备份不完整或来源不同 | 停止恢复流程，改用更早的合法备份，不覆盖现有库 |
| 报表数字与预期不符 | 交易类型选错、币种混加、期初未核对 | 按第 7、8 章复核，用正确领域纠错并留审计 |
| 页面样式异常、功能缺失 | 静态资源未回写或缓存了旧构建 | 重新回写 wwwroot 并强制刷新浏览器 |

### 4.3 端口占用判定逻辑

启动器不会只看端口是否被监听，还会判断占用者身份：

- 后端：命令行必须包含 PersonalFinance.Api 且包含该项目的路径，同时 /api/health 返回健康，才认定为"本项目健康实例"并直接复用。
- 前端：命令行必须匹配 vite 的入口脚本，且页面与 /api/health 均正常，才认定为可复用。
- 任一条件不满足即报错退出，并明确说明不会强行结束占用进程。
- 桌面版「个人记账」（%LOCALAPPDATA%\Programs\PersonalFinance，快捷方式参数 --desktop）默认占用 5080；本副本自 1.0.0 正式版（2026.11.18.1）起改用 5085，两者可同时打开。2026-11-18 及以前本副本也用 5080，同时打开时后启动的一方会报「后端端口 5080 已被占用」，表现为打不开。

### 4.4 数据库相关排查

- 服务名固定为默认实例；命名实例或远程实例不在本机支持范围内。
- 启动器读取的是后端开发配置中的连接项，环境变量可覆盖它；要求数据源为本机、库名为 PersonalFinanceWeb，不符合即拒绝启动。
- 拒绝的理由是安全：宁可不启动，也不把数据写到错误的库。
- 结构落后时不要手工改表，走第 6 章的结构升级流程。

### 4.5 登录与会话排查

登录依赖后端受保护的密钥配置与会话表。密钥缺失或轮换后，既有会话会全部失效，表现为登录后立即掉线或刷新失效。处理原则：

- 密钥以受保护配置或进程环境提供，不写进日志、命令行与源码。
- 恢复或迁移后应主动让旧会话失效，并要求重新登录。
- 具体密钥材料与存放位置不在本文记录，参见部署文档。

### 4.6 页面 404 与空白页

- 静态资源路由仅在 wwwroot 存在时生效；缺失时后端只提供 API，浏览器访问首页即 404。
- 前端路由为单页应用，深链接由后端回退到 index.html 处理；以 /api 开头的未知路径按接口 404 返回，不会被回退成页面。
- 浏览器强制刷新与清理缓存可以排除"服务端已更新、客户端仍是旧包"的假象。

### 4.7 复制或移动目录后启动失败（静态资源清单）

后端编译时会把静态资源的根目录按**绝对路径**写进 `bin/Debug/net10.0/PersonalFinance.Api.staticwebassets.runtime.json`。因此把整个目录复制或移动到别处、却沿用复制来的编译产物时，后端仍然从原路径读前端文件：表现为后端能启动、接口正常，但页面是旧版本，`/release-info.json` 报的是旧发布号。

- 判定：对比 `PersonalFinance.Api.staticwebassets.runtime.json` 的 `ContentRoots` 与当前目录是否一致。
- 处理：在新目录里重新构建后端（`dotnet build backend/src/PersonalFinance.Api/PersonalFinance.Api.csproj -c Debug`），让清单按新路径重新生成；`wwwroot` 本身不必重新同步。
- 不要只改 JSON 里的路径：第二个根目录 `obj/Debug/net10.0/compressed` 里的 gzip 变体仍对应旧内容，会出现压缩版旧、明文版新的不一致。
- 同一次构建若恢复出其他平台的运行库，可按需清理 `runtimes` 下非本机目录，但必须保留 `runtimes/win/lib/net9.0/Microsoft.Data.SqlClient.dll`；删掉它会直接以 `Could not load file or assembly 'Microsoft.Data.SqlClient'` 启动失败。

### 4.8 报障时应提供的信息

只提供错误码、traceId、发生时间、程序版本、库别名与操作步骤；**不要**发送账务明细、截图中的真实金额、连接信息或任何密钥材料。

## 5. 数据库备份与恢复

> **适用场景**：升级数据库结构前、重要数据调整前、定期归档、以及需要把数据恢复到某个历史时点时使用本节。

### 5.1 备份目录约定

| 场景 | 目录 | 文件命名 |
| --- | --- | --- |
| 脚本备份 | backend/.backups/<时间戳>_<编号>/ | database.bak 与 manifest.json 成对出现 |
| 升级前备份 | backend/.backups | PersonalFinanceWeb-before-migrate-<年-月-日-时-分-秒>.bak |

脚本备份每次新建一个以 UTC 时间戳加随机编号命名的目录，备份文件与清单一同落盘；目录结构本身就是"同一次备份"的证据。部分目录里只有清单与错误日志，表示那次备份失败或文件已转移，不能当作可用备份。

### 5.2 升级前备份（双击入口）

"备份并升级本地数据库.bat"的真实行为：

1. 要求输入大写 YES 才会继续，避免误触。
2. 检查 dotnet 与后端 DLL 是否存在。
3. 用 sqlcmd 以本机管理员身份连接默认实例，对 PersonalFinanceWeb 执行带 INIT 与 CHECKSUM 的完整备份。
4. 对刚生成的备份执行 RESTORE VERIFYONLY 校验。
5. 校验通过后以 Development 环境执行后端结构升级命令。
6. 任一环节失败即停止，并提示保留备份、查看上方错误、不要重复执行。

【停机】该脚本应在前后端都已停止时执行，避免备份过程中仍有写入。

### 5.3 脚本备份

```powershell
# 默认实例、默认库名；脚本只接受 PersonalFinanceWeb
pwsh -NoProfile -File .\backend\scripts\backup-finance.ps1

# 显式参数形态（与脚本参数一致）
pwsh -NoProfile -File .\backend\scripts\backup-finance.ps1 -Server . -Database PersonalFinanceWeb

# 查看历史备份清单
pwsh -NoProfile -File .\backend\scripts\backup-history.ps1
```

备份脚本的设计要点：

- 只接受 PersonalFinanceWeb，库名不符直接拒绝，避免把隔离库或临时库当成正式库备份。
- 从不覆盖既有备份，每次新建目录。
- 备份使用 COPY_ONLY 与 CHECKSUM，不打断既有备份链。
- 备份后立即做 VERIFYONLY，并计算文件摘要写入清单。
- 清单中记录业务指纹（关键表行数与金额摘要），供恢复后比对。
- 费用附件存放在数据库表的二进制字段中，随库一起备份，不需要单独拷贝附件目录。

### 5.4 恢复前置检查

恢复属于【不可逆】操作，动手前逐项确认：

1. 前后端均已停止，没有写入者。
2. 已确定要用的备份编号，且该目录内 backup 文件与清单都完整。
3. 清单状态为已通过校验，摘要可复算。
4. 明确本次恢复的目标库名，绝不使用正式库名做试验。
5. 若目标是覆盖现有库，必须由数据责任人明确确认，并说明覆盖后丢失的时间窗口。
6. 如果备份之后产生了新流水，禁止直接用旧备份覆盖，应改为导出差异或人工补录。

### 5.5 隔离恢复验证

```powershell
pwsh -NoProfile -File .\backend\scripts\verify-finance-restore.ps1 -BackupId <备份编号>
```

脚本会新建一个以 RestoreCheck 前缀加随机编号命名的隔离库并恢复进去，恢复过程不使用覆盖选项，因此不可能影响正式库。校验内容包括：

- 恢复是否成功、校验和是否一致、文件列表是否可读。
- 数据库完整性检查是否通过。
- 约束、迁移记录是否与备份时一致。
- 关键表行数与金额摘要是否与清单中的业务指纹一致。
- 附件数量与内容摘要是否一致。

结论中的各项通过标记全部为通过，才算备份可用；任一项不一致都必须查明原因，而不是"先恢复再说"。

### 5.6 恢复后核验清单

1. 迁移记录与目标程序版本匹配。
2. 关键表行数与恢复前一致（或与预期差异一致）。
3. 账户余额与恢复前核对一致。
4. 附件可正常打开。
5. 旧会话已失效，用户重新登录。
6. 记录本次恢复的时间、备份编号、执行人与结论。

### 5.7 加密备份与保留策略

- 加密备份脚本支持加密与解密两种模式，输入输出均为文件，密钥由环境变量提供，不写在命令行与文档里。
- 密钥丢失等于备份不可恢复，密钥必须与备份介质分开保存。
- 保留建议：日备保留一周、周备保留两个月、月备保留一年；具体配额按磁盘容量调整，但不得把唯一有效备份当作可清理对象。
- 备份必须离机保存一份；同盘保存不算备份。

### 5.8 禁止事项

- 禁止删除、移动、重命名 backend/.backups 下用途不明的目录与文件。
- 禁止用恢复覆盖正式库来"试试看"。
- 禁止把备份文件、清单或密钥上传到公开位置。
- 禁止在应用库中执行仓库根目录的旧建库脚本。

## 6. 更新与回滚

> **适用场景**：发布新版本、升级数据库结构、或需要退回上一个可用版本时使用本节。

### 6.1 标准更新流程

1. **备份**：按第 5 章完成一次脚本备份，并做隔离恢复验证。
2. **停止**：执行 -Mode Stop，确认状态为已退出。
3. **更新源码**：把新版本文件放入仓库对应目录，不覆盖正在运行的目录。
4. **构建后端**：dotnet build backend/src/PersonalFinance.Api --no-restore。
5. **构建前端**：在 frontend 目录执行生产构建，构建脚本会先校验版本公告，再做类型检查与打包。
6. **回写静态资源**：把 frontend/dist 复制到 backend/src/PersonalFinance.Api/wwwroot。
7. **升级数据库结构**（仅当新版本要求）：用"备份并升级本地数据库.bat"或命令行方式执行。
8. **启动**：-Mode Start -Static。
9. **验收**：健康检查、首页、登录、关键业务页面逐项确认。

### 6.2 前端生产构建

```powershell
# 版本公告校验 + 类型检查 + 打包
pnpm --dir frontend run build

# 构建产物校验（含版本公告产物是否生成、是否未被离线缓存）
pnpm --dir frontend run verify:build
```

构建脚本会先执行版本公告校验，任何一条公告不合规都会让构建失败；因此"先改公告再构建"是硬性顺序。

### 6.3 回写与重启

```powershell
Copy-Item -Path .\frontend\dist\* -Destination .\backend\src\PersonalFinance.Api\wwwroot -Recurse -Force
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Stop
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\scripts\PersonalFinance.Local.ps1 -Mode Start -Static -NoBrowser
```

静态模式不会热更新：不回写、不重启，浏览器看到的仍是旧包。

### 6.4 数据库结构升级

两条合法路径：

- 双击"备份并升级本地数据库.bat"，走备份、校验、升级的完整链路（推荐）。
- 手工执行示例：

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Development"
dotnet .\backend\src\PersonalFinance.Api\bin\Debug\net10.0\PersonalFinance.Api.dll --initialize-db --contentRoot .\backend\src\PersonalFinance.Api
```

约束：

- 结构升级只允许作用于库名以 PersonalFinanceWeb 开头的库。
- 迁移命令有独立超时设置，默认十分钟，可在后端配置中调整到 30 秒至 1 小时之间。
- 升级前必须先构建后端，否则运行目录缺少编译期产物，进程会在启动阶段直接失败。
- 升级失败时保留备份、保留错误输出，不要反复重跑。

### 6.5 回滚

| 变化类型 | 回滚方式 | 注意事项 |
| --- | --- | --- |
| 仅前端静态资源 | 用上一版 dist 回写 wwwroot 后重启 | 无需动数据库 |
| 后端程序 | 换回上一版 DLL 或整目录后重启 | 保持配置与静态资源同版本 |
| 配置变更 | 恢复变更前的配置副本 | 恢复前比对摘要，确认是同一份 |
| 数据库结构 | 一般不回退结构 | 优先判断新旧程序是否兼容；数据已写入时禁止用旧备份覆盖 |
| 完整版本回退 | 按上一版目录启动 | 启动后立即做健康检查与关键页面验收 |

回滚的硬规则：

- 数据已产生新流水时，不允许用旧备份覆盖正式库来"回滚"。
- 结构升级通常不可逆，回滚前先确认旧程序能否读新结构。
- 每次回滚都要记录时间、版本、原因与验收结论。

### 6.6 发布验收清单

1. /api/health 返回 healthy 且 code 为 READY。
2. 首页可打开，静态资源无 404。
3. 登录、登出、刷新后会话正常。
4. 记一笔收入与一笔支出，余额变化符合第 8 章规则。
5. 版本更新页可打开且显示本次公告。
6. 检查一次备份是否可验证（必要时）。

## 7. 账户与分类维护规范

> **适用场景**：新增账户、调整账户状态、整理分类、合并重复项时使用本节。

### 7.1 账户建立规则

- 一个真实资金容器对应一个账户：银行卡、支付账户、现金、信用卡分别建账。
- 账户名使用"机构 + 用途"的可识别写法，不写完整卡号、不写支付口令、不写身份证号。
- 账户类型与币种在建账时确定；有历史数据后不允许修改类型或币种。
- 期初余额代表"开始记账那一刻"的余额，是历史数据与系统数据的分界。
- 预付款类账户只对应单一合同或单一用途，不要混装多个合同。

### 7.2 账户状态维护

| 操作 | 允许条件 | 处理方式 |
| --- | --- | --- |
| 改名 | 随时 | 只改显示名，不影响历史 |
| 停用 | 余额为可用状态、无未结清业务 | 停用后不再出现在新增选择中 |
| 关闭 | 余额归零、无未结清与未核销 | 关闭前核对余额与未结清项目 |
| 改类型 / 改币种 | 不允许 | 需要换口径时新建账户并做转移 |

停用与关闭之前，必须核对余额、未结清的分期与报销、未核销的预付款，否则会造成"账上还有钱但账户已关闭"的矛盾状态。

### 7.3 分类规则

- 分类只服务收入与支出，转账、借贷本金、报销收回等不计入收支的场景不使用消费分类。
- 分类最多两层；超过两层的诉求应当用标签或项目维度解决。
- 父子分类同时用于预算时，注意不要重复叠加额度。
- "不明消费"是待整理项，不是长期分类；每月清理一次。
- 停用分类不应破坏既有退款与原消费的关联，停用前确认没有进行中的关联业务。

### 7.4 合并与清理

- 同名或近似分类先合并引用再删除，合并前预览受影响记录数量。
- 商户、项目、标签是补充维度，不替代分类。
- 调整统计口径前，先核对受影响的报表与历史对比，确认口径变化是"看得懂"的。

### 7.5 定期自查

- 每月核对账户余额与真实余额，差异超过一分钱要查明来源。
- 每月检查一次异常资金：大额、负数余额、跨币种、长期挂账。
- 每季度检查一次停用账户与停用分类，确认没有仍在引用的项。

## 8. 财务数据核算规则

> **适用场景**：核对数字、判断某笔业务该记在哪、怀疑报表口径、或准备纠错时使用本节。

### 8.1 余额口径

账户余额 = 期初余额 + 该账户全部未删除交易的明细金额之和。

- 明细金额带符号：资产类增加为正、减少为负；负债类金额按有符号累计，欠款增加体现为负债增大。
- 删除交易后余额随之变化，删除是软删除，历史可追溯。
- 汇总报表与账户余额使用同一口径，不另设第二套算法。

### 8.2 金额精度

| 规则 | 取值 |
| --- | --- |
| 录入小数位 | 最多两位 |
| 整数位上限 | 十八位 |
| 正数业务 | 必须大于零 |
| 展示格式 | 固定两位小数 |
| 折算金额 | 按四位小数参与计算 |

规则由后端统一校验，前端提示只是提前告知；错误提示形如"金额必须大于零，最多两位小数""金额格式无效"。

### 8.3 交易平衡

每笔交易至少包含两条明细，且各明细按基准金额折算后之和必须为零，否则报"交易金额未平衡"。这条规则是双分录的落地方式：有借必有贷，跨账户、跨币种都必须配平。

### 8.4 币种规则

- 账户币种必须是系统支持的定义之一。
- 记账币种必须与资金账户币种一致，避免在账户内部产生隐式汇率。
- 多账户混合付款要求同币种。
- 退款必须与原消费同币种。
- 外币金额按原币保存，并记录明确的汇率时点；缺价格或缺汇率时报表显示"未知"，不得默认按 1 处理。

### 8.5 幂等与并发

| 机制 | 规则 | 失败表现 |
| --- | --- | --- |
| 幂等键 | 长度 1 至 150，服务端按方法、路径与请求体计算摘要；同键同请求返回已存结果 | 同键不同请求返回 409，错误码为幂等冲突 |
| 操作指纹 | 必须是 64 位小写十六进制 | 格式不符直接拒绝 |
| 乐观并发 | 请求携带数据版本，与库中版本不一致即拒绝 | 409，提示"数据已更新，请刷新后重试" |
| 用户级锁 | 写操作按用户加排他锁，超时十秒 | 超时返回冲突，可重试 |
| 协作锁 | 协作类写操作额外加协作锁 | 同上 |

### 8.6 事务与隔离

写操作在一个数据库事务中完成，隔离级别为读已提交；事务内完成业务写入与审计写入，提交失败则整体回滚，不留半条记录。

### 8.7 用户隔离与审计

- 所有查询按当前登录用户过滤，跨用户读取在数据访问层就被限制。
- 关键写操作在同一事务内写入审计记录，包含操作者、类型、对象与时间。
- 审计表只追加，不提供删除入口。

### 8.8 禁止的直接改库

- 禁止用 SQL 直接修改金额、余额、交易明细、审计记录。
- 纠错必须走对应业务领域：退款走退款、冲销走冲销、导入恢复走既有服务。
- 任何绕过服务层的直改都会破坏幂等、版本与审计三条约束，后续报表将无法解释。

### 8.9 报表口径提示

- 预算、预留、目标与预测属于规划，不增加净资产。
- 仅统计标记的账户只提供口径参考，不计入资产。
- 冻结金额只影响可用余额，不改变账户余额。
- 工资条与社保档案只是记录，不自动生成收入。

## 9. 版本与更新公告

> **适用场景**：发布任何用户可见的功能、优化或修复时使用本节；文档内部调整不需要发布公告。

### 9.1 版本号规则

- 版本号形如 YYYY.MM.DD.N：四位年份、两位月份、两位日期、当日序号，序号从 1 开始递增。
- 日期按 Asia/Shanghai 的实际发布日填写，不得使用计划日期。
- 同一天第二次发布，序号加一；不得复用旧版本号。
- 另有一个产品版本号，形如 x.y.z，与前端包版本保持一致。

### 9.2 公告数据结构

frontend/src/data/releases.json 中维护一个当前版本字段与一个公告数组；数组第一条即当前版本，历史条目按时间倒序排列。每条公告至少包含：唯一 id、发布日期、类型（新增 / 优化 / 修复）、中文与英文标题、中文与英文更新内容、产品版本号。

校验脚本会检查：

| 校验项 | 规则 |
| --- | --- |
| 包版本一致 | 前端包版本必须等于产品版本号 |
| 当前版本格式 | 必须匹配年月日加序号格式 |
| 首条即当前 | 公告数组第一条的版本必须等于当前版本 |
| 日期一致 | 当前版本中的年月日必须与首条公告日期一致 |
| 序号字段 | 发布序号必须等于当前版本 |
| 产品标识 | 产品名与发布通道须为约定值 |
| 唯一性 | id 与版本号不得重复 |
| 排序 | 日期严格降序，产品版本号同样降序 |
| 类型取值 | 只能是新增、优化、修复三者之一 |
| 内容长度 | 每条 1 至 30 条要点，中英文均非空且不超过 5000 字符 |

### 9.3 发布公告操作步骤

1. 在公告数组最前插入一条新公告，填写 id、日期、类型、中英文标题与变更要点。
2. 更新当前版本字段为首条公告的版本。
3. 同步更新产品版本号与前端包版本。
4. 执行前端生产构建，构建会先跑版本公告校验。
5. 构建通过后回写 wwwroot 并重启。
6. 打开版本更新页确认公告显示正确。

公告内容不得包含凭据、密钥、真实用户账务或内部服务器路径。

### 9.4 阅读入口

| 入口 | 位置 | 说明 |
| --- | --- | --- |
| 应用内版本更新 | /settings/updates | 登录后在设置中查看，带应用框架 |
| 公开公告页 | /updates | 独立页面，登录页也有入口，可未登录阅读 |

两个入口读取同一份数据源，内容必须一致。

### 9.5 构建期公告产物

- 生产构建时会把公告数据额外生成一个静态文件 release-info.json，与前端包一同产出。
- 前端"检查更新"读取该文件，且请求显式禁用缓存。
- 开发模式下该请求由本地中间件直接响应，同样带禁止缓存的响应头。
- 构建校验会断言该文件确实生成，并且没有被离线缓存清单收录，避免用户看到过期公告。

手工验证：

```powershell
Invoke-WebRequest http://127.0.0.1:5085/release-info.json -UseBasicParsing | Select-Object StatusCode
```

### 9.6 发布检查表

1. 公告已新增且版本唯一。
2. 日期为真实发布日。
3. 生产构建与构建校验均通过。
4. 静态资源已回写并重启。
5. 两个公告入口均可打开且内容一致。
6. 健康检查与关键业务页面验收通过。

## 10. 安全检查清单

> **适用场景**：每次发布、每次对外提供资料、每次交接与备份时逐项对照。

### 10.1 绝不外传的内容

| 类别 | 具体内容 |
| --- | --- |
| 凭据 | 数据库口令、证书口令、备份加密密钥、任何访问令牌 |
| 配置 | 连接字符串、内部服务地址、服务器路径、部署脚本中的内部参数 |
| 数据 | 真实账户名、真实账务金额、真实身份证件信息、附件原文 |
| 产物 | 备份文件、备份清单、审计导出、日志原文 |

### 10.2 配置与密钥管理

- 连接信息与签名密钥只以受保护配置或进程环境提供，不写进日志、命令行、源码、文档。
- 修改配置前先保存副本并计算摘要，便于比对与回滚。
- 密钥轮换后主动让旧会话失效，并确认所有人都重新登录。
- 备份加密密钥与备份介质分开保存，任何一方丢失都视为备份不可用。

### 10.3 备份与介质

- 至少一份备份离机保存，禁止把备份放在同一块磁盘上作为唯一副本。
- 定期做隔离恢复验证，只校验不恢复等于没验证。
- 备份目录的访问权限按最小必要授予；备份管理员与普通使用者权限分离。
- 不删除用途不明的文件与目录；不确定就先备份再问。

### 10.4 日常检查节奏

| 周期 | 检查项 |
| --- | --- |
| 每日 | 健康检查、数据库服务状态、最近一次备份是否通过校验、磁盘剩余空间、日志中的异常条目 |
| 每周 | 做一次隔离恢复验证；检查计划任务是否正常触发；复核异常资金记录 |
| 每月 | 核对账户余额与真实余额；清理"不明消费"；检查停用账户与分类；归档旧日志 |
| 每季度 | 复核权限分配；复核密钥与证书有效期；复核备份保留策略是否仍满足容量 |

### 10.5 只读审计

```powershell
pwsh -NoProfile -File .\backend\scripts\stage-z-audit.ps1 -Database PersonalFinanceWeb -OutputFile .\backend\.runtime\audit.json
```

审计脚本按一组只读规则检查数据一致性，输出违规条目；违规数必须为零才可认为数据健康，脚本不会自动修复任何数据，发现违规先报告再决定处置。

### 10.6 事故处置顺序

1. 停止写入（停服务）。
2. 保全现场（备份、日志、审计导出），不做破坏性排查。
3. 判断影响面：是否涉及真实账务、是否涉及凭据、是否涉及数据丢失。
4. 先恢复可用性，再修复根因；恢复过程遵守第 5 章的前置检查。
5. 记录时间线、处置动作与结论，更新交接文档。
