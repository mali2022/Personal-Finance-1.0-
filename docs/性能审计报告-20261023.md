# 性能审计报告

审计日期：2026-10-23（Asia/Shanghai）  
对象：Personal Finance 全项目；线上 6.9.3 / 2026.10.23.5。  
性质：源码审查、现有实测证据复核、生产只读资源快照。不是所有模块均已完成压力测试的证明。

## 1. 执行结论

当前主要风险是磁盘容量、异常查询尾延迟、自动轮询与请求取消链路。普通交易列表已具备服务端分页和页内关联加载；异常查询仍明显更重。建议先处理容量和请求放大，再优化 SQL 执行计划，最后评估需要失效机制的预计算。不能以延长浏览器超时替代优化。

本次审计未修改或部署业务代码。上一轮列表匹配范围复用仍仅在本地，线上未包含该项优化。本报告没有把本地候选性能当作线上性能。

## 4. 分层审计

### 4.1 前端加载、缓存与渲染

已具备路由懒加载、图表引擎拆包、服务端分页（20/50/100条）、查询缓存与静态资源版本化。

当前dist入口index-C0o4Wp3J.js为916122字节，gzip测量318042字节；framework-CELQssq_.js为222295字节，gzip69244字节。这是磁盘产物压缩估算，不是线上实际传输量，也没有计入全部动态依赖。较大的图表包不等于全部参与首屏。

frontend/src/main.tsx默认staleTime=30000，同时refetchInterval=30000、窗口聚焦刷新、重连刷新、失败重试1次。30秒缓存并不意味着页面长期停留时没有请求。建议将自动轮询限于确需实时状态的页面，目录采用较长缓存和写入失效；交易页按用户操作与写入事件更新。验收应记录停留5分钟请求数和多标签页并发。

TransactionIntegrityPanel.tsx在折叠状态下也启用issues和matches查询。建议展开后加载；切换交易时保持用户隔离与正确key。不要仅使用CSS隐藏来替代懒加载。

PWA已排除API请求缓存、静态资源按版本缓存；截图曾出现旧页脚版本，需测试更新提示及刷新后的资源一致性。不能将旧页面缓存误判为后端修复无效。

### 4.2 API与取消链路

前端列表/统计传递AbortSignal，但TransactionWorkspaceEndpoints与FinanceService相关查询没有把RequestAborted传到EF异步调用。浏览器取消请求后，服务端查询未必及时停止。建议贯通CancellationToken至数据库，并验证取消后的活跃SQL与CPU回落。

默认Axios超时15秒、Nginx模板proxy_read_timeout 120秒、负载脚本60秒，三者口径不一致。建议保留交互请求明确预算，重任务通过异步作业和进度返回，重试应避免重复放大慢查询。

### 4.3 数据库与异常规则

重复检测已改分组关联，异常ID合并使用Concat，外层Contains维持成员判断语义。统计已复用匹配ID；本地列表也已尝试同样复用。这些改善仍不能消除全量规则扫描。

FinanceDb.cs当前交易索引包含UserId/OccurredAt/Id、UserId/AccountId/Status、UserId/ImportJobId。重复规则使用账户、类型、金额、币种、时间、商户；现有索引与该分组并不完全对应。建议先抓执行计划和逻辑读，再试验覆盖/筛选索引，衡量写入、导入、磁盘成本；未获得执行计划前不直接判定缺少某个索引就是全部瓶颈。

Balance/Category/Transfer规则涉及分录相关子查询；Merchant涉及目录计数；TransactionIssues按8条规则串行查询。应逐规则计时，定位最昂贵规则，验证按交易集合聚合分录是否更优。

matchedIds采用ToArrayAsync全量收集，再Contains回查。40k测试有效，但10万/100万匹配ID的内存、SQL参数体积和计划稳定性没有证据。候选方案包括服务端临时结果、分批或持久化异常结果。持久化必须覆盖交易编辑、退款、目录/分类变化、时间规则跨日和多用户隔离，不能以陈旧异常结果换速度。

### 4.4 报表、账户、导入导出

ReportsService近期交易Take(10)，FinancialReportCenter商户榜Take(30)，AccountStatistics部分图表已数据库分组和Take(10)，这些有明确边界。

报表多次聚合以及账户合同/还款计划集合仍需大目录专项测试。不能仅因存在ToArrayAsync认定全表加载或N+1，需结合查询范围和执行计划。

CustomReportExportService将预览序列化为JsonElement、枚举为数组，再在内存构建CSV/Excel，最终ToArray保存文件；存在多份内存表示。100000行上限在预览完成后校验，不能保证预览阶段内存受限。建议前置行数/字节限制、CSV流式输出，大Excel异步生成，测试峰值内存与取消。

导入清理查询有分页；本次未对大CSV、附件OCR、工资导入或恢复重试作负载测试，应纳入后续矩阵。

### 4.5 后台任务

RecurringScheduler与BudgetAlertScheduler使用每批100用户及取消令牌，是已有保护。AiAgentWorker每2秒轮询、有MaxConcurrentRequests上限、工作流Take(100)、数据库应用锁和租约恢复逻辑。

AI调度循环包含迁移检查，工作流逐项检查/创建；高任务量下数据库往返和锁占用需测量。未证实当前存在阻塞。应记录队列等待、执行时间、重试率和任务并发，避免只统计HTTP延迟。

### 4.6 部署资源

2026-10-23约19:39只读快照：40GB根盘已用约37GB，98%，可用约1.1GB；内存总3627MB、available约1297MB，swap已用437MB；API约291MiB、SQL约1.448GiB。负载均值0.17/0.14/0.16、瞬时容器CPU较低，只说明采样时相对空闲。

此前部署备份因写入失败中断，清理构建缓存后完成；当前空间又紧张，单次清缓存不构成长效解决。应在下次发布前核算备份、解压、镜像和回滚需要的峰值空间，配置磁盘告警与留存策略。保留已验证备份和可用回滚，采用异地备份及容量扩展；本审计未删除文件或扩容。
