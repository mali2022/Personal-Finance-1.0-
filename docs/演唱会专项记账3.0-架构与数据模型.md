# 演唱会专项记账3.0：架构与数据模型

2026-11-01，当前增量实现，不代表全部领域完成。

真实资金仍来自 FinanceTransaction；ConcertScene、MusicTopic、MusicBrandLink、MusicPurchase、MusicBudget 等复用现有 StoredDocument。禁止创建第二套真实账本。

本轮 ConcertOrder 末尾增加可空 Tickets：ConcertTicket(Id,Tier,Seat,Attendee,Format,State)。旧JSON缺少该字段按空集合处理，不伪造逐票资料。记录数可少于订单Quantity，未登记部分留待用户补录；不能超过Quantity，场次内票ID须有效且唯一，已保存票ID不可移除。此轮没有逐票实付分配，不将票数或状态加入 EffectiveCosts。订单付款与退款继续按原订单资金关联核算。

票状态：Pending→Received→Used；Pending/Received可Cancelled；Used/Cancelled终态。可补录历史状态。Received/Used须订单Issued/Used，Used须演出已开始。Format为Electronic或Paper。TicketsUpdated审计保存所属订单、修改前后值；随既有Write事务提交。接口沿用POST/PUT /api/concerts及原版本、幂等、用户隔离机制，无新增路由。

无需DDL迁移。隔离SQL测试从现有迁移建库，覆盖无Tickets旧档案保存、逐票补录与读取、状态校验、财务金额不变；未在正式数据库应用迁移。未执行旧版本客户端降级写入测试；旧客户端若遗漏已保存门票，服务端会拒绝删除，避免静默丢失。

独立巡演当前仍只有场次TourId/TourName字段，完整巡演实体、艺人成员和多艺人场次尚未实现。后续需基于当前源码设计兼容引用，不把GUID格式校验当成参照完整性。
