## 1. 现状审计与复用

以当前源码为准审查了路由、导航、ReconciliationPage、TransactionsPage、ImportPage、交易/导入特性、FinanceDb、事务写入、审计、幂等及权限服务。旧版账户对账主要负责账户余额核对与调整；交易完整性面板已有人工账单关联；导入中心已有真实解析、字段映射、预览、去重、商户归一、清洗历史及正式入账。百万级合成账本工具和 SQL 集成测试直接保留并复用。

升级保留 `/reconciliation`、`/import`、原余额调整、旧账单匹配 API 和正式交易模型。新增外部证据模型，不复制余额或正式交易事实；匹配确认只写关系与并发版本，撤销不回滚或重写账务分录。旧关联和新关系互相检查，防止同一交易/参考号重复占用。

高风险改动：导入中心目的隔离、共享账本权限、已有交易的匹配版本联动、大表参考号索引、跨期入账余额调节、批量部分失败。均有服务端检查；生产部署仍需单独授权。

## 4. 匹配算法与安全边界

候选先按用户、账户、币种及发生/入账日期窗口阻断，最多读取 101 笔用于识别截断；向客户端返回最多 100 个候选。金额用 decimal 与现有 Money 解析，无浮点账务计算。实际账户分录的剩余可分配金额决定容量，而非交易展示金额。文本采用 Unicode NFKC、大小写与标点规范化，并复用明确商户别名。

规则得分：金额 40，日期最多 15，标准化商户一致 20/包含 10，唯一参考号 20，类型 5，备注 5，封顶 100。高阈值只能配置为 80–100，中阈值下限 55。得分是确定性规则分，不是概率。已知账户、方向、币种、对方信息或账务结构冲突不应自动确认。

组合建议最多 12 个候选，深度 2–3，最多 20 个组合；组合仅供人工审核。显式分配最多 40 条边、20 个来源和 20 笔交易，检查双方符号与剩余容量；支持一对多、多对一、多对多、部分金额、多支付来源和账户转账两端。退款须有合理原支出，转账/还款必须有正确双端及平衡分录。手续费按账户实际分录检查，不擅自补记。

自动确认默认关闭。服务器必须核准精确用户/账户/文件 SHA/字段映射 SHA、审核人和过期时间。此核准是离线文件审核，不代表银行联网或银行签名。自动规则还必须限定普通 Expense/Income、精确商户/类型/参考号、零金额容差、日期最多 3 天；唯一高置信候选、优先级不冲突、无截断/人工修正/复杂业务/外币手续费/多支付等。用户需先看自动执行预览，再显式执行；服务端执行前逐条重验审批和版本。普通建议任务不会自动确认。

确认和撤销复用逐用户 SQL 应用锁、事务、幂等键及请求指纹。不同用户仍隔离。服务端校验来源版本、交易版本和共享财务空间权限；不接受客户端评分作账务依据。支持网络重试、相同键重放、不同请求体冲突与并发竞争。批量中每项先做完整安全预检，禁止因中途发现受限对象而半撤销组合来源。

## 6. 银行余额调节口径

输入 openingBalance 为银行期初余额。银行侧日期取 PostedAt，缺失才取 OccurredAt；系统侧取正式交易发生日。系统期末来自现有 Balance 服务，系统期初为期末减期间账户分录净变动。

银行期初 + 非忽略来源期间净发生额必须等于银行期末。银行侧本期流水扣除已与期末前系统交易匹配的金额，系统侧本期分录扣除已与期末前银行流水匹配的金额，分别得 BankOnly / LedgerOnly。跨期但截至期末已结清的关系不再误计为未达项。

调节差额 = SystemClosing + BankOnly − BankClosing − LedgerOnly。零差额本身不足以完成：期间必须已结束、无版本冲突、来源期初/期末流水一致；所有未达/忽略项需显式理由复核，最多200项，否则先匹配或缩小期间。预览 token 绑定版本及证据，再保存快照；不创建余额调整分录，不将覆盖率当作余额核对成功。

## 7. 前端流程

现有账户入口 → 选择账户 → 外部流水导入 → 真实文件上传/映射预览 → 分批接收 → 候选与解释 → 人工理由及确认 → 历史/异常 → 撤销重开 → 余额调节快照。保留原余额调整区，明确这是另一项会写账务的原功能。

工作台七个区域、分页与状态搜索、批次选择、手工分配、规范化修正、规则与审批状态、任务历史、异常、余额报告。交易完整性面板按需加载新来源关系。React Query 保存后刷新相关列表/余额/历史，无全局轮询。360px 采用区域选择器和单列候选布局；主题沿用项目设置，新增文案兼容现有中英文机制。

## 10. 迁移前检查、备份、回滚与恢复

1. 获取正式发布/迁移授权，核对环境与库身份，禁止将隔离测试连接串或凭据写入公告。
2. 备份正式数据库和当前应用包，保留原有备份；用 SQL Server RESTORE VERIFYONLY 及隔离恢复验证可恢复性，记录校验值和迁移基线。
3. 在恢复副本核对历史迁移顺序、外键/分录完整性、交易及分录计数、各账户余额；执行生成的幂等升级 SQL 后重验这些账务不变量。
   同时检查已有 `Database:SnapshotReads` 配置及数据库快照隔离状态；本次隔离验收启用快照读，不能只复制应用配置而遗漏数据库设置。默认来源可信审批为空，部署不得自行开启自动确认。
4. 大表 Transactions 参考号索引会扫描数据并可能占锁、消耗日志和 tempdb；在维护窗口构建，依据正式 SQL Server 版本评估 ONLINE/RESUMABLE 支持，不能直接假定 LocalDB 的耗时适用生产。
5. 先部署兼容候选到演练环境，验收后按现有备份发布流程发布；本次没有执行这些生产步骤。
6. 应用回滚优先还原旧应用包并保留新增证据表。若已产生正式对账证据，不直接执行 Down 丢弃表；先停止写入并导出/备份来源、关系、审批、任务及审计，再决定补丁恢复或经授权回退数据库。
7. 如确需结构回退，在恢复副本验证逆向迁移至 `20261026112139_ComplexTransactionQueryIndexes`；撤销新索引和新表会丢失对账证据，不能仅因旧包可运行就执行。优先保留新增表。
8. 任务重启后读取已有进度并继续下一步；同一请求用原幂等键重试，不能盲目重发新键。原始来源保持不变，匹配撤销走业务接口且保留理由。

### 金额方向及精度补充

未映射明确方向时，负数保留原始负号，不能将负收入或负退款悄悄改为正数。正数转账缺少明确方向时不接收，要求先映射收付方向。显式方向把原始负数解释为流入时，来源仍可由人工复核，但自动确认明确阻止。自动确认同时要求有效的原始事实指纹，旧来源缺少指纹时保留人工处理路径。

候选差额以精确 decimal 字符串传输，避免浏览器 JSON 数值精度损失；服务端计算继续使用 decimal。转换器兼容读取早期数值形式的候选证据。固定金额约束按来源流水原始总金额的绝对值判断，不会误用部分匹配的剩余额度。

### 核心账本性能改动补充

对已有 TransactionLedgerAnomalies 查询进行等价重构：分录合计、无效分类和转账两端先分别在 SQL 内聚合，再关联交易。保留所有原有校验条件，没有按金额阈值跳过记录，没有全量加载账本到应用内存。新增 LedgerAnomalyEquivalenceTests，使用独立的逐交易 EF 规则对照正常及异常样本，检查删除状态和多用户隔离。

隔离库原始 SQL：约10.1秒、CPU约6.4秒、发生临时工作文件溢写；重构 SQL：约5.3秒、CPU约3.5秒、工作文件溢写为0。重构增加了部分顺序读取，并非所有逻辑读取量都下降；最终 API 矩阵实测见下节。试验性覆盖索引没有稳定收益，已从隔离测试库移除，没有纳入发布迁移。

重复候选查询先用 SQL CHECKSUM 缩小可能重复的集合，落入连接内临时表后，再按全部原始业务字段分组并作空值安全的精确比较；哈希碰撞不能成为重复结论。独立对照测试包括 `a-b` 与 `ab` 等碰撞样本、空商户、日期偏移、删除状态及用户隔离。CHECKSUM 的碰撞限制参见 [Microsoft 文档](https://learn.microsoft.com/en-us/sql/t-sql/functions/checksum-transact-sql?view=sql-server-ver15)。该优化没有新增持久大表索引。

### 最后安全修正

- 无参考号来源的稳定身份使用文件哈希和原始行号；每批最多200行，并有界核对已有来源的导入原始行。兼容旧身份哈希，重新映射同一文件不会产生第二条有效来源；事实变化返回冲突。两个原始行即使内容完全相同仍分别保留，重复文件重传按原始行去重。
- 精确参考号先通过索引查找，再加入日期阻断候选；日期窗口外参考号仍可进入人工复核。参考号与普通候选总量受限，截断不能自动确认。
- 对方账号只有末四位时保持“未核实”，不能误判为完整账号验证成功。
- 部分匹配来源已有关系指向改动或删除的交易时，禁止继续分配，先处理冲突。
- 余额快照持久保存当时的覆盖率与期间证据；后续撤销不会重写已完成快照。发生日与银行入账日跨期分别纳入，期初银行余额、银行期间净流水与期末余额必须自洽。
