# 专项记账候选模块清单（2026-11-16）

本文只是候选清单，**未实现、无版本号、不构成发布公告**。信息来源：本轮对现有源码与交接文档的只读核对；代码出处标到行，未核实的标「待验证」。

## 1. 现在的模块形态（可核对）

- 模块开关只有演唱会一个布尔：`backend/src/PersonalFinance.Api/Application/ConcertModels.cs:5` 的 `public sealed record ConcertModules(bool Concerts = false);`。
- 读写入口 `GET/PUT /settings/modules`（PUT 在 `backend/src/PersonalFinance.Api/Application/ConcertEndpoints.cs:92`），返回 `{ version, concerts }`（`backend/src/PersonalFinance.Api/Application/ConcertService.cs:14`）。
- 前端靠它决定页面是否可用：`frontend/src/pages/ConcertsPage.tsx:41-45` 用 queryKey `['optional-modules']` 读同一接口，`const enabled = modules.data?.concerts === true;`。

结论：现在是「一个专项 = 一个布尔 + 一套专用端点和页面」，不是「一个专项 = 一条配置」。

## 2. 已有可复用的原语

演唱会专项已经沉淀出这些结构，新专项能否便宜落地取决于复用其中几个：

## 3. 方向 A：先把专项泛化成引擎（成本随专项数线性，只有这一步能改掉）

把 `ConcertModules(bool Concerts)` 扩成模块列表（`{ modules: [{ kind, enabled, template }] }`）+ 类型模板，页面与报表按 kind 渲染。

- 收益：第 4 个以后的专项从「复制一套端点 + 页面 + 测试」变成「加一条配置与报表字段」。
- 代价：动的是已有 890 处演唱会代码引用的既有契约（`GET/PUT /settings/modules` 响应体、`ConcertsPage.tsx:45` 的读取方式），需保持旧响应兼容。
- 推翻条件：如果只打算再加 1 个专项，泛化的成本高于直接复制。

## 4. 方向 B：候选专项（按复用度降序）

1. **剧场 / 音乐剧 / 脱口秀 / 音乐节** —— 与演唱会同构，主档 + 场次 + 逐票 + 分摊全可用；缺口只在「非票务的收入项几乎为零」。成本：低（几乎改类型枚举）。风险：与现有演唱会页面是否合并，是产品决策（待验证产品意图）。
2. **体育赛事（含客场行程）** —— 复用主档 + 逐票 + `/concerts/trips`。缺口：赛季/主客场归类。成本：低到中。
3. **旅行（一趟行程的账本）** —— `/concerts/trips` 已是雏形，但真要按行程记账还需要分摊与人均。成本：中；缺口是「行程内每笔支出如何与全局账不重复」的口径问题（与现有归集门禁同类）。
4. **人生仪式（婚礼、满月、升学宴：份子钱收付）** —— 复用赠送、转让、联合分摊。成本：中；缺口是收付双向语义（现有 gift/transfer 只覆盖出票方向）。
5. **大件与装修（报价、定金尾款、分批到货、维保到期）** —— 复用 `/concerts/payables` 与附件、变更历史。成本：中；缺口是分期与到期提醒。
6. **藏品（手办、球鞋、卡牌：买入、估值、出手盈亏）** —— 复用 `/concerts/collections` 与 collection-purchase。成本：中；缺口是估值快照而非成交价（现有收藏偏「买到用掉」）。
7. **宠物 / 牙科等长期复诊（周期性支出 + 报销）** —— 复用应付与退款、附件。成本：中到高；缺口是周期性计划，现有专项都是一次性事项。
