# 百万级复杂查询专项优化（2026-10-26）

本轮从 6.10.0 源码与生产一致的快照读取配置开始，目标是解决上一轮 8 并发矩阵的 11 次超时：金额排序 4 次、广泛搜索 5 次、账户筛选 2 次。所有规模测试只使用随机命名的独立测试数据库，没有导入正式账务。

## 数据与测量约束

重新生成 1,000,000 笔交易、2,000,000 条分录，覆盖 2018–2025 年、三种币种、60 个账户、264 个分类和 200 个资料项。API 使用 Release 构建与 SQL Server LocalDB；本机为 16GB 内存、Core Ultra 5 225。该 Express/LocalDB 版本的执行计划不使用并行查询；机器还运行日常应用，结果不能视为生产吞吐保证。

沿用六类查询及 1/4/8 并发、每个工作线程三轮的矩阵：普通列表、深分页、金额倒序、广泛匹配关键词、无结果关键词、账户筛选。客户端期限保持 15 秒，失败不重试、不隐藏。完整矩阵另包含 100 次逐模块与详情探测，总计 334 次。

本轮基线 234 次复杂查询中有 18 次超时，分布于 4/8 并发的金额排序与广泛搜索。与历史 11 次的差异反映运行状态、缓存及数据标识重新生成的影响，不把它们当作严格相同条件的加速比。

原始记录位于本地 `verification/million-20261026/million-query-20261026`。每个阶段记录查询参数、状态、P50/P95、最大值和实际 DLL 指纹；SQL 采样保留执行计划、CPU、逻辑读取和耗时。私有会话凭据不随站点发布。

## 定位与实现

1. **金额排序**：原选页 SQL 需要大范围排序，观测约 61,529 个逻辑页、2.4 秒 CPU。新增按用户、金额、创建时间与 ID 排序的覆盖索引，保留稳定排序；观测同类选页 SQL 使用 4 个逻辑页。该数字仅指选页 SQL，完整响应仍包含精确余额等计算。
2. **账户筛选**：转入账户缺少对应索引，关联集合需要扫描。新增按用户、转入账户与时间排列的过滤覆盖索引，保持主账户、转入账户及分录账户均能被查到。
3. **广泛搜索**：原广泛命中计数约 100,691 个逻辑页、4 秒 CPU，重复执行文本及分类/标签匹配。先在当前筛选范围内证明交易主账户均已被关键词命中，再省略恒真的关键词分支。证明由数据库按请求执行，不跨请求缓存，不假定外键归属，其他条件继续生效。
4. **年度复盘**：同一期间的汇总、趋势与年度预算重复计算。只在同一次读取中显式传入完全相同的已计算结果；未结束年度仍使用预算的完整年度范围。独立报表与复盘内嵌结果逐字段比较。
5. **完整矩阵发现的长尾**：分类概览省去不参与汇总的商户与账户明细字段；账户汇总与历史余额明确交易用户条件，帮助使用覆盖索引；商户异常检测先查询真正重名的有效商户资料，没有歧义时不扫描百万交易。未登记商户、其他类型及其他用户的同名资料不会误报。
6. **首页与净值归因**：诊断定位首页最近交易隐式使用时间倒序、ID 正序，无法匹配已有索引，单条选页 SQL 约 6.3 秒。改为与交易列表一致的时间、创建时间、ID 倒序。净值归因复用本次读取已有的期末估值，当前账本净值只计算所选币种账户；统一资产估值仍保留其他币种及其缺失汇率覆盖信息。

没有使用脏读、跳过锁定行、放宽期限或不精确计数，没有删减分录及历史余额字段。

## 回归与中间结果

新增和扩展的测试覆盖：搜索在写入后重新计算、筛选和删除视图；余额的相同时刻、创建时间与 ID 次序、午夜和时区、分账户付款、回溯修改；复盘与独立报表的完整及部分年度一致性；分类概览与详情的退款、优惠、收入和层级统计一致性；商户检测的用户及资料类型隔离。

一次区间余额聚合方案虽然结果正确，但金额排序页被优化器选成重复查找，发生性能回退，已经撤回，相关证据保留。最终继续使用原有精确的自然日余额算法。

第二轮候选的 234 次复杂查询全部通过，8 并发 144 次零超时；完整 334 次仅年度复盘一次超时。后续候选解决年度复盘，但出现首页、分类概览、汇总的长尾，因此继续补充上述优化，没有把中间结果标为最终通过。

持续写入后的中间复测同样保持 8 并发零超时，完整矩阵剩首页及净值归因两次长尾。单请求 SQL 诊断（单独允许等待语句完整结束，不作为验收）中，修正后首页由 13.69 秒降至 7.48 秒，净值归因由 14.59 秒降至 11.12 秒，分类概览为 4.64 秒。正式验收仍使用 15 秒期限。新增测试逐字段比较复用估值与独立计算，并确认首页最近交易和默认交易列表顺序一致。

## 服务器备份重建

按用户明确要求，清理范围为本项目数据库备份、旧发布回滚目录及旧回滚镜像标签，不涉及其他应用、数据库卷或正式账务。

为保证重建期间始终有可用恢复资料，先运行既有备份流程并完成 SQL Server `RESTORE VERIFYONLY`，再保存应用、配置与数据保护密钥的恢复归档及 SHA-256 清单。校验线上版本、目录边界、文件类型与旧备份未变化后，才删除已盘点的旧副本。

首次重建已验证：删除 35 个旧备份文件、14 个旧回滚目录、12 个旧回滚镜像标签；保留一个过渡数据库备份及一组恢复资料，可用空间约 21GB。

发布后已为 **6.10.1** 再次完成备份与校验，并删除 3 个过渡备份条目（包括过渡恢复目录与发布前数据库备份）、1 个本次发布回滚目录和 1 个回滚镜像标签。截至本次操作，服务器仅保留 **1 份新数据库备份、1 组新恢复资料**；旧回滚目录与回滚标签均为零，可用空间约 **20.3GB**。

恢复资料包含应用与配置、数据保护密钥、实际 nginx 配置及 TLS 证书材料，均存于私有目录；目录权限 700、文件权限 600。数据库备份经过 SQL Server 可读性校验，数据库文件与三份恢复归档均有 SHA-256 清单。线上版本、运行构建指纹在操作前后保持一致，API 健康。

备份校验不等同于完整的恢复演练；本轮没有在正式账务上进行还原操作。
